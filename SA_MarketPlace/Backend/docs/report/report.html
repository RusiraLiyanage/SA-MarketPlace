SA Marketplace — Delivery Report

Consumables ordering and marketplace for Collection Manager: the backend and the customer marketplace, seller portal and SA Admin front ends. What was built, why, how to run it, and what comes next.
Prepared for: Tech Lead  ·  Prepared by: Rusira Senath Liyanage  ·  Status as at: 25 October 2026  ·  Source of truth: Intern Project Brief, 15 July 2026

1. Summary

The brief asks for one shared backend with several front-end entry points: a marketplace for any buyer, a seller side with admin verification, and consumable ordering inside Collection Manager (CM). The Phase 1 backend for the marketplace, seller portal and admin app is complete, tested and documented, and the customer marketplace, the seller portal and SA Admin front ends are built on top of it and work end to end against the real API. The CM store front end has not been started. Nothing has been deployed; everything runs locally as the brief requires.

Three things to know up front

  1. Two Phase 1 items are deliberately not built: CM ordering (needs the CM front end and a decision on single sign-on) and adding stock to the buyer's inventory when an order is received. Both are recorded as open decisions, not forgotten (section 7).
  2. One deliberate departure from the brief's wording: the catalogue requires a sign-in, so there is no anonymous browsing. Anyone can still register with an email and password, with no CM account needed (ADR 0021).
  3. Three of four front ends exist. The marketplace for buyers, the seller portal and SA Admin are built and connected (section 3, "Front end"). The CM store is next (section 8). Prioritised recommendations and risks are in section 9.

2. Set it up on your own machine

This is the whole path from an empty folder to a running system. Allow about 15 minutes, most of it the first pnpm install (it downloads Chromium for the invoice PDFs). Everything runs locally; nothing is installed system-wide except the three tools below.

One Postgres 16 container serves all three APIs. docker-compose.yml defines it, and its settings come from your .env.

4

Start the database and wait until it is healthy

pnpm db:up
docker compose ps        # STATUS should read "healthy"
5

Create the tables by running the migrations

pnpm --filter @sa-marketplace/entities migration:run

This runs the 20 migration files in packages/entities/src/migrations in timestamp order, one line per file ("… has been executed successfully"). The database is changed only this way, never by hand (ADR 0001). The result is 17 tables and 7 enum types.

6

Load the demo data (the seed)

pnpm db:seed             # prints: Seed applied successfully.

This runs packages/entities/src/seeds/seed.sql in one transaction, so a failure leaves the database untouched. It replaces the seeded tables, so running it again resets the demo data. Everything is fictional.

7

Confirm the database is correct

pnpm db:verify           # runs scripts/verify-schema.sql: every row must read PASS (33 checks)
pnpm --filter @sa-marketplace/entities db:check   # boots the database module and connects

The 33 checks cover the schema shape, the ban on storing card details, and the business rules the data must obey (for example, prices frozen on orders, unapproved sellers' products invisible).

2.8 Real email (optional)

Reset-password emails are sent through a Gmail account when it is configured, and are only logged otherwise (ADR 0046). In Google Cloud create an OAuth client (Web application) with the redirect address http://127.0.0.1:53682/callback, enable the Gmail API, add the sending account as a test user, and put the client ID and secret in Backend/.env (GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET). Then run pnpm mail:token, sign in as the sending account, and restart the API; it saves the refresh token and sender address for you. While the OAuth client is in Testing mode the token expires after 7 days. Seeded addresses are fictional, so register a buyer with an inbox you own to see an email arrive.

4. Architecture

The brief's most important rule is one system with several entry points, not systems that sync. The backend is a pnpm and Turborepo monorepo of three NestJS apps over shared packages and a single PostgreSQL database.

How the code is organised

  • One module per business area inside each app (auth, products, cart, checkout, orders, catalogue, suppliers…), each with controller, service, DTOs and types, so a feature can be found and changed in one place.
  • Shared behaviour lives in packages, not copied between apps: the one shared rule for "is this product orderable" is used by the catalogue, the cart and checkout.
  • The same order, invoice and stock rules serve every app. The buyer and the seller download the very same stored PDF.

No anonymous browsingThe catalogue needs a sign-in (ADR 0021). Easy to relax for the public storefront if wanted.
Email is opt-inReset emails go through a Gmail account when configured (ADR 0046) and are logged otherwise. The Google OAuth client is in Testing mode, so its token expires every 7 days (run pnpm mail:token again). Gmail has sending limits; use a transactional provider for a real marketplace. A "your password was changed" email is not built.
Rate limits are in memoryFine for one local instance; a shared store (Redis) would be needed to run several instances.
Local-development caveats.env.example carries a development JWT secret (replace it for anything shared). Restarting dev servers can leave old Chromium processes running. The end-to-end tests expect seeded data.
Back-in-stock alertsNot built. It needs a table of who is waiting, an endpoint, and an email when a supplier restocks (about half a day now that email exists). Until then out-of-stock products show a disabled button.
CM store front endNot started. The customer marketplace, the seller portal and SA Admin have front ends.
Admin sign-up is a speed bumpRegistration only checks the email's domain (ADR 0038); nothing proves the person owns the mailbox, so anyone can create anything@sampleassist.com.au and approve suppliers. Acceptable for local fake data, and it must be replaced before real use, for example by an existing admin approving each new admin or by a verified email.
Approving a supplier cannot be undoneThere is no suspend or offboarding in Phase 1, so a wrong approval has no fix from the screens. The pop-up says so before it is confirmed.
SA Admin on small screensThe navigation adapts below 992 px but the pages are desktop-only, as in the seller portal. Responsive layouts are Phase 2.
Seller portal on small screensThe navigation adapts below 992 px but the pages are desktop-only: tables scroll sideways. A seller filling the long product form can also be signed out by the 15-minute session and lose it. Responsive layouts are Phase 2.
Pick list is not savedThe ticks live on the screen only; the backend has no status for "picking". A refresh forgets them.
Seeded product imagesThe seeded products point at image files that do not exist, so the browser logs a failed request for each and cards show a category icon instead. Products created through the seller API show real images.
Retiring a listing is finalIn Phase 1 a retired product is read-only and cannot be published again.

9. Recommendations

In the order I would tackle them. The first four unblock the rest of the project.

#RecommendationWhy, and who
1Merge phase-1-completed into main through a reviewed pull requestThe brief wants work to land on main by pull request and never broken. The branch now holds the backend and both built front ends; it is large, so review it in the commit order set out in docs/report/pull-request-guide.md rather than as one diff. Make the merge check: type check, lint, db:verify and every test suite on a freshly seeded database. Tech lead.
2Settle the two open decisions before building CM(a) How CM users sign in: does an SSO-provisioned user also get a password, or does the marketplace accept SSO? (b) Inventory: what marks an order "received", and how does CM record consumption, since stock can otherwise only go up. These shape the CM screens and the data flow. Tech lead with the CM team.
3Build the CM store nextThree front ends now prove the structure and the API (section 8.1). Decide first whether they share a workspace package: three copies of about 35 files is where copying stops paying off, and a fourth would make it worse. None of the front ends has page tests (see Quality above), so a small end-to-end suite against the seeded API would close that gap for all of them. The CM store also needs recommendation 2 settled first.
4Use a separate test databaseThe end-to-end tests expect the seeded data, so manual testing on the development database makes some fail, and one test asserts the database name. A dedicated test database (for example set through DB_NAME) keeps development data safe and makes the suites repeatable.
5Add automated checks when the team is readyThe brief rules out CI/CD for now. Later, a pipeline running lint, type check, unit and end-to-end tests on a fresh database would have caught the one clean-checkout bug found during handover.
6Decide on anonymous browsingThe catalogue needs a sign-in today (ADR 0021). If the public storefront should be browsable without an account, relax that rule and keep checkout signed in. Product decision.
7Tidy the development defaultsReplace the development JWT_SECRET in .env.example with a placeholder, and have each developer generate their own.
8Revisit sessions now that the front end existsAdd refresh tokens only if the 15-minute sign-out hurts. The design is recorded in ADR 0045.
9Handle the Google credentials safelyKeep them only in .env. Delete any OAuth client whose secret was shared outside the team, publish the OAuth app or use a transactional provider if the 7-day token expiry becomes a nuisance, and never commit the refresh token.
