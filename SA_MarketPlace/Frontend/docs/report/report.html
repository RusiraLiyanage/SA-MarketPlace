SA Marketplace — Front-end Hand-over Report

The customer marketplace, the seller portal and SA Admin: what was built, why, how to run it, how it was checked, and what comes next. It covers the three React apps only; the backend has its own delivery report.
Prepared for: Tech Lead  ·  Prepared by: Rusira Senath Liyanage  ·  Status as at: 27 October 2026  ·  Source of truth: Intern Project Brief, 15 July 2026

1. Summary

The brief asks for one shared backend with several front-end entry points. Three of the four entry points now exist as React apps on top of the Phase 1 backend: the customer marketplace for buyers, the seller portal for verified suppliers, and SA Admin for Sample Assist staff. Every screen in their designs is built and connected to the real API, with no sample data or fake backend, and each app was checked in a browser against the seeded database. The Collection Manager (CM) store, the fourth surface, has not been started. Nothing is deployed; everything runs locally, as the brief requires.

Four things to know up front

  1. The CM store is not built. It is blocked on two open decisions (how CM users sign in, and how CM inventory decreases), both in the backend report. The three built apps are the template for it (sections 8 and 9).
  2. Pages and the Redux store have no automated tests. The 746 tests cover helpers, forms, tables, dialogs and layouts. Pages that call the API are checked in a browser against the real API, with a written walkthrough for the seller portal and SA Admin. An end-to-end suite is the main quality gap (section 6).
  3. About 35 generic files exist in three copies (table, pagination, dialog, layouts, hooks, the API client) because a shared package was deliberately not built. A fix to one must go into all three. Whether to extract a package before a fourth app is an open decision (section 5).
  4. Where a design and the backend disagree, the backend wins. Each app's plan lists every difference: 34 for the seller portal and 20 for SA Admin, with the customer app's in its plan and in section 3 below.

2. Set it up on your own machine

Allow about 15 minutes, most of it the backend's first install. The front ends need the backend running, because none of them has sample data.

2.1 What you need

pnpm10.17.1Pinned in each package.json; corepack enable installs it
Docker Desktopany recentFor the backend's Postgres only. Must be running

2.2 Start the backend, then a front end

1

Start the backend (database, migrations, seed data, three APIs)

cd SA_MarketPlace/Backend
cp .env.example .env
pnpm install
pnpm db:up && pnpm --filter @sa-marketplace/entities migration:run && pnpm db:seed
pnpm dev

pnpm dev runs all three APIs in one terminal. Use it or the three single commands (pnpm customer-facing, supplier-api, admin-api), never both: they share ports and build folders and restart each other in a loop.

2

Start a front end, one terminal each for the ones you want to see

cd SA_MarketPlace/Frontend/customer-facing-frontend   # or seller-portal, or admin-portal
pnpm install
pnpm dev

No .env is needed: the default API address is the local backend. Copy .env.example to .env only to change VITE_API_URL (the seller portal also has VITE_SUPPORT_EMAIL).

3

Open VS Code on the app's own folder

Not the repository root: the root window pins the Backend's TypeScript 4.9, which cannot read the front ends' config and shows false "cannot find module" errors.

2.5 A ten-minute walkthrough that crosses all three apps

  1. Buyer. In the customer app sign in as j.shaw@saclinics.com.au. Search the shop, filter by category and price, open a product, add two items from different sellers (one from Bindi MedSupply), and check out with the declined card (the cart stays intact), then with the approved card. A cart with two sellers becomes two orders.
  2. Seller. In the seller portal sign in as priya@bindimedsupply.com.au. The new order is on the dashboard with an SLA countdown. Open it, tick the pick list, and dispatch; the invoice can then be downloaded.
  3. Buyer again. In the customer app, My orders now shows the order as dispatched, with the same invoice PDF.
  4. Admin. In SA Admin sign in as a.morgan@sampleassist.com.au. Orders lists every order across sellers, with CSV export and the same invoice.
  5. Verification. In the seller portal register a new business. It lands on "under review". In SA Admin open Suppliers, review it, tick the three checks (Approve unlocks), and approve. Sign in to the seller portal again: the seller sees the approval notice once, then the dashboard. Reject a different one to see the reason on the seller's screen.
Approve and reject send an email to the applicant and cannot be undone from the screens (there is no suspend in Phase 1). The pop-ups say so. With no email settings the message is printed in the API terminal instead.

The customer marketplace

Thirteen designed screens, all built: catalogue, product detail, cart, checkout (delivery and payment), order confirmation, My orders, order detail, add-to-cart states, items-per-page dropdown, login, register and edit profile.

TopicWhat was done
Stack and structureReact 19, Vite, TypeScript, Ant Design 6, styled-components reading the Ant Design tokens through ThemeBridge, Redux Toolkit with RTK Query in the CM's feature-folder shape (actions, slice, selector, types). A store used by one page lives in that page's folder.
API and sessionsOne client turns every failure into one error shape and shows the backend's own message. The token lives in sessionStorage; a rejected token ends the session with "Session expired"; sign-out clears all cached data. Guards send visitors to sign in and back.
Where the backend wonGST is the total divided by 11; no supplier rating; the backend's password rule, card rules and statuses; no current-password field on change password; no PO number; invoice offered only after dispatch; no "Notify me" (it promised an alert that never came).
Backend changes it neededAn order-number search on GET /orders, the invoice file name exposed over CORS, and optional real email. All small, additive and tested.
Colour and accessibilityThe brand blue was darkened to #0958d9 so white text passes WCAG AA (6.5 to 1). axe runs in a test on every page and pop-up; skip link, one h1 per page, announced page titles, named dialogs, labelled fields.

The seller portal

Eighteen designed screens, all built, plus a reset-password page and a retire pop-up that the designs did not include. A single gate sends a seller to the right place after sign-in: the portal, or the screen that says where their application stands.

TopicWhat was done
Stack and structureBuilt from the customer app with a left sidebar (a menu button and drawer below 992 px) and the seller's orange. The dashboard shows live counts and the orders to dispatch, closest deadline first.
Where the backend won34 differences are listed in the plan. For example: no "product categories" or "role" box on sign-up (the profile derives categories from products), dispatch sends no email, status screens say "Sample Assist", and sellers set prices directly.
Colour and accessibilityWhite on the brand orange is only 2.4 to 1, so buttons use near-black text and orange text is the darker #ad4e00. axe found four issues in the final pass (unlabelled read-only fields, a details list without terms, colour-only links, placeholder contrast); all fixed.
Behaviour worth knowingConfirm dispatch stays disabled until every pick-list item is ticked, with a warning that says why. Price and stock are read-only in the catalogue list and changed on the edit page. A failed dispatch from the queue is shown, never silent.
Backend change it neededOne line: Content-Disposition exposed over CORS so the invoice keeps its name.

SA Admin

Eleven designed screens, all built: sign-in, register, supplier verification (queue, empty queue), application review with approve and reject pop-ups, all orders (and its empty state), order detail and My profile, plus the forgot and reset password pages.

TopicWhat was done
Stack and structureBuilt from the seller portal with its own purple and a sidebar of Suppliers (with a pending-count badge), Orders and My Profile.
Where the backend won20 differences are listed in the plan. The main ones: no "keep me signed in"; no invitation code on register (the backend requires a terms tick and a staff email domain); only the name is editable on the profile; no "Invite administrator" card; order filters use the backend's real payment statuses and fulfilment stages.
The verification checklistThree tick boxes on a pending application. Approve is disabled until all three are ticked, with a notice beside the boxes saying why; Reject is always available. The ticks are not saved, because the backend has no field for them, so this only guards against an accidental approval and does not prove the checks were made.
Decisions it makes safeBoth decisions email the applicant and cannot be undone here, and the pop-ups say so. A decided application shows who decided it, when, and the reason given. If another admin decides first, the screen shows the backend's 409 message and refreshes.
Backend change it neededOne line: Content-Disposition exposed over CORS so the CSV export and the invoice keep their names.
AccessibilityThe purple #722ed1 is 6.9 to 1 against white and needed no workaround. axe found no violations on 20 signed-in pages and pop-ups, or on the five public pages.

4. Architecture

Each app is an independent single-page application with the same shape. A page reads the store through RTK Query hooks; the hooks call one API client; the client calls that app's API and nothing else.

Folder shape, the same in all three

Folder (under src)What lives there
router/routes.tsx declares the whole route tree once (pages load lazily); paths.ts holds every URL, so a route change is one file; handle.ts gives each route its title and breadcrumbs
pages/One folder per screen, each with its own components/ and __tests__/. Modals/ holds the pop-ups, each with its own route
components/Shared SA-prefixed parts (SATable, SAPagination, SADialog, SAPageHeader…) and layouts/. Anything used on one page stays in that page's folder; two or more moves here
store/Redux features (actions = RTK Query endpoints, slice, selector, types) and the store setup
infra/The API client (http.ts, api.ts, errors.ts) and pagination.ts, the backend's paging contract
hooks/ utils/ patterns/ constants/ styles/Helpers; utils/format.ts formats money, dates and counts; styles/theme.ts is the app's Ant Design token set

Routes at a glance

AppRoutes
Customer/shop, /shop/products/:id, /cart (+ remove and clear pop-ups), /checkout/delivery, /checkout/payment (+ declined), /checkout/confirmation/:order, /orders, /orders/:order (+ reorder), /profile (+ sign out); public: /login, /register, /forgot-password, /reset-password, /session-expired
Seller/ (dashboard), /application and /application/resubmit (before approval), /orders, /orders/:order (+ cancel), /catalogue, /catalogue/new, /catalogue/:id, /catalogue/retire/:id, /profile (+ sign out); the same public pages
Admin/suppliers, /suppliers/:id (+ approve, reject), /orders, /orders/:order, /profile (+ sign out); the same public pages

5. Decisions and why

These shape the front ends most. The seller portal and SA Admin keep the full list in their ui-build-plan.md (section 8, "Decisions (settled)").

DecisionWhyIndustry practice followed
Ant Design is the only UI library; one theme token set per appThe brief says marketplace, seller and admin use Ant Design with a distinct primary colour each, so the surfaces read as separate products. A colour change is one token.Design tokens; a single component library.
styled-components reads the Ant Design tokensStyles sit at the bottom of the component file as in Collection Manager, and both libraries read one theme, so nothing drifts.Design-token theming; co-located styles.
RTK Query for every API callCaching, loading and error states and re-fetching on change come from one tool, in the feature-folder shape the CM already uses.Server state kept apart from UI state.
No sample data, no fake backendA mock hid real mismatches. Removing it meant every screen was checked against the real API and its real errors.Test against the real contract.
The backend wins over the designsThe API enforces the rules (GST, passwords, statuses, who may do what). A screen that promised otherwise would mislead, so each difference is written down per app.One source of truth for business rules.
Pop-ups are routesA pop-up is a child route of the page it opens over (/cart/remove/:id), so Back closes it and a link can open it. All use SADialog: an icon, a one-line summary, what changes, what stays the same, and equal buttons with the safe choice first.URL as state; consistent confirm-dialog pattern.
Ask before losing editsPages that edit saved data (customer profile, seller product form and business profile, admin profile) use useUnsavedChanges: leaving asks to keep editing, discard or save; closing the tab gets the browser's own warning.Unsaved-changes guard on forms.
Never disable a control without saying why nearbyA greyed button with no reason is a dead end. Confirm dispatch and Approve supplier each carry a notice that says what unlocks them.WCAG: operable, understandable controls.
The access token lives in sessionStorage; sessions are 15 minutes with no renewalIt ends with the tab, and the backend revokes tokens on sign-out and password change. "Keep me signed in" was left out because the backend does not support it (ADR 0045), and showing it would mislead.Short-lived tokens; do not offer what the API cannot do.
Copy the generic files, do not share a packageThe brief says the CM and marketplace deliberately share no component library, and a package for one team's first three apps was more machinery than the work needed. Cost: three copies of about 35 files (a fix goes into all three). Open decision before a fourth app.Rule of three for extraction.
Latest releases; TypeScript 7 compilesThe apps start on current versions (pnpm outdated prints nothing). typescript is aliased to the 6.0 package so typescript-eslint can read it until it supports 7.Stay current; keep the toolchain working side by side.
No enumserasableSyntaxOnly is on, so as const objects and string unions replace enums.Types that erase to plain JavaScript.

Security on the front end

ConcernControl
Who can see whatThe API decides; the front end filters nothing itself. A route guard sends visitors to sign in, and the seller portal's gate keeps unapproved sellers off the portal. Another user's record answers 404, which the pages show as "not found".
Tokens and secretsNo secrets in any front end. The token is in sessionStorage, sent as a Bearer header, and cleared on 401 or sign-out. .env is git-ignored; .env.example holds only an API address.
Card dataThe payment form posts to the mock API; nothing is stored in the browser, and the backend keeps only the last four digits and the brand.
InputForms validate (email, password rule, ABN checksum, lengths) for speed, and the backend validates again for safety, and its messages are shown as written. React escapes everything it renders; no HTML is injected.

7. Known limitations and open items

ItemState and what is needed
CM store front endNot started. Needs the two decisions in the backend report (single sign-on, and how CM stock decreases).
No page or store testsCovered by browser walkthroughs only. A small end-to-end suite (for example Playwright) against the seeded API would close this for all three apps.
Pages are desktop-onlyBelow 992 px the navigation adapts, but tables scroll sideways or squeeze and cards crowd. Responsive layouts are Phase 2 (brief).
15-minute sessionsNo refresh tokens (backend ADR 0045). A seller filling the long product form, or an admin editing a name, can be signed out and lose it. Saving a draft often is the workaround.
Admin sign-up is a speed bumpIt only checks the email domain, so anyone can create anything@sampleassist.com.au and approve suppliers (backend ADR 0038). Fine for local fake data; replace it before any real use, for example an existing admin approving each new admin.
The admin checklist is not savedIt gates Approve on the screen but nothing records that the checks were made. Saving it needs a backend field.
Approve and reject cannot be undoneThere is no suspend or offboarding in Phase 1. The pop-ups say so before confirming.
The pick list is not savedThe ticks live on the screen; the backend has no "picking" status. A refresh forgets them.
Seeded product images do not existCards show a category icon and the browser logs a failed request per image. Products created in the seller portal show real pictures.
Backend gaps the screens exposeNo "delivered" action; no storage conditions or shelf life on a seller's product form; no choosing a primary image; no "Notify me" when out of stock; no change of sign-in email; reset emails only if Gmail is configured.
Large exportsThe backend refuses a CSV over 10,000 rows before sending anything; the screen shows its message. Narrow the filters.
Three copies of about 35 filesA fix goes into every copy. One bug fix already had to be made in two apps.
